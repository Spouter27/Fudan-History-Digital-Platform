## 1 当前工程与建设范围

### 1.1 已有能力

以下结论来自本次源码核对。测试结果引用已有[联调验证记录](../backend/验证记录.md)，不是本次重新进行的全量测试。

| 部分 | 当前真实实现 | 当前限制 |
| --- | --- | --- |
| 前端运行 | React、TypeScript、Vite、HashRouter | 页面集中在App.tsx，尚无统一工作区 |
| 时间轴 | 时期/主题/关键词筛选，年/十年分组，详情和出处 | HTML/CSS列表，无连续缩放、平行史料泳道 |
| 人物关系 | SVG节点、拖动、缩放、筛选、人物详情 | 预设坐标，没有D3自动力导向 |
| 搜索 | 前端searchCatalog函数；后端也暴露/api/search | 前端仍主要检索已加载目录，非服务端分页搜索 |
| 投稿审核 | 投稿、通过、退回、撤回、删除、导出 | 退回后没有原条目编辑重新送审 |
| 身份 | 随机密码开发账号、scrypt摘要、会话Cookie | 不是学校邮箱验证或SSO |
| 权限 | 服务端所有权、成员/审核员、状态冲突检查 | 无正式账号管理；审核员可审核自己的投稿 |
| 数据库 | node:sqlite、WAL、5张表、参数化查询、事务 | catalog_items按JSON保存；无增量迁移体系 |
| 问答入口 | /api/qa/retrieve返回检索线索及出处 | 关键词检索，answer=null，无Embedding或LLM |
| 测试 | 前端8项逻辑测试，后端4组接口集成测试；有本地浏览器记录 | 无仓库CI、正式性能或跨浏览器验收 |
| 备份 | 修改前项目ZIP、SQLite在线备份命令 | 需要建立长期保留策略与恢复演练 |

内置12个事件、8个人物、11条关系、3份来源全部为虚构演示。不能把演示数据作为真实校史知识库或对外史学成果。

### 1.3 一期与后续范围

**一期核心**：可追溯校史目录、人物和事件、中文搜索、投稿审核、正式身份与权限、数据导入、可恢复部署。

**一期条件允许再做**：基于已核准资料的RAG问答。先验证检索与引用，再做生成。

**二期**：校园历史地图、个人记录助手、社群协同编辑、复杂关系推理、移动端专门产品。预留数据扩展点，不提前开发整套空框架。

不将“引入某个库”当作验收结果。验收应描述用户能完成什么、内容依据是什么、失败时如何处理。

## 2 架构决策与技术选型

### 2.1 总体结构

~~~mermaid
flowchart TB
  Browser[React前端]
  Proxy[Nginx 同源入口与HTTPS]
  API[Express模块化API]
  Catalog[目录和搜索模块]
  Auth[身份与权限模块]
  Submission[投稿审核模块]
  QA[RAG与只读Agent模块]
  DB[(本地SQLite 或正式PostgreSQL)]
  Files[(受控史料文件存储)]
  Import[数据校验与导入命令]
  Model[外部Embedding与生成模型]
  Browser --> Proxy
  Proxy --> API
  API --> Catalog
  API --> Auth
  API --> Submission
  API --> QA
  Catalog --> DB
  Auth --> DB
  Submission --> DB
  QA --> DB
  QA --> Model
  Import --> DB
  Import --> Files
~~~

开发环境仍由Vite把/api代理给后端；正式环境由Nginx提供静态前端并代理/api。一个后端进程承载多个业务模块，避免学生团队维护多个网络服务。

### 2.2 关键决策

| 决策 | 选择与原因 | 触发重新评估的条件 |
| --- | --- | --- |
| 仓库 | 单仓库，pnpm workspace管理前后端和共享协议 | 真正独立团队、独立发布周期出现 |
| 后端 | Express模块化单体，复用现有代码和测试 | 模块边界成熟后仍出现难以管理的依赖问题 |
| 数据访问 | 当前SQLite；迁移PostgreSQL时选pg参数化SQL与显式迁移 | 团队有明确ORM经验并证明减少维护成本 |
| 数据库 | 一套PostgreSQL负责结构化数据，RAG阶段启用pgvector | 容量或查询复杂度经测量超出能力 |
| UI | 继续现有CSS；拆CSS模块与设计变量 | 复杂表单/弹窗显著增加时评估组件库 |
| 前端数据状态 | React本地状态＋按需引入TanStack Query | 请求缓存、并发刷新、失效规则明显复杂 |
| 图表 | 一期保留SVG与列表时间轴 | 节点规模、碰撞和交互要求超出当前实现 |
| 会话 | 服务端会话＋HttpOnly Cookie | 有多端独立客户端等明确需要时再评估其他方案 |
| 检索 | 先关键词与结构化条件，再混合检索 | 有足够真实语料和问答评测集 |
| Agent | 有上限的白名单只读工具循环 | 评测证明多步查询比固定流程确有收益 |
| 运维 | 单机Docker Compose、数据库备份、结构化日志 | 多实例与高可用成为实际需求 |

**为何不立即回到原计划全部技术栈**：NestJS、Prisma、Redis、D3、LangChain、PostGIS同时引入，会把已有经验拆散。现在的主要问题是代码集中、协议重复、真实资料缺失和生产能力不足；换框架不能直接解决这些问题。

明确选择PostgreSQL阶段使用pg而非同时引入Prisma，是为了保持目前参数化SQL和事务的学习路径。若团队后续决定使用ORM，先做单模块试验，再通过ADR替换该决策。

### 2.3 工程原则

1. 一个业务模块有清晰的入口、业务规则、数据访问和测试。
2. 类型共享不等于权限共享；授权必须由服务端根据当前身份判断。
3. 公开读模型与内部管理数据分开，默认不返回邮箱、密码摘要或内部备注。
4. 发布、撤回、来源权限变化都必须同步影响展示、搜索和问答。
5. 一次PR尽量只改变一个维度：目录、业务、数据库、依赖升级不要同时大改。
6. 每个新依赖记录用途、版本、替代方案与移除条件。
7. 复杂度由具体需求驱动；暂无需求的模块只写接口说明，不创建大量空文件。

### 3.2 一个模块内部如何组织

以投稿模块为例：

~~~text
backend/src/modules/submissions/
  routes.ts                HTTP路径与中间件绑定
  controller.ts            读取请求、调用服务、构造响应
  service.ts               状态、所有权、事务用例
  repository.ts            数据访问接口与当前实现
  policy.ts                谁可以执行什么动作
  mapper.ts                内部行记录转公开/私有DTO
  submissions.test.ts      核心业务测试
~~~

只有功能变复杂时才拆出controller/policy/mapper。简单只读模块允许routes、service、repository三个文件，避免一行逻辑一个文件。

### 3.3 依赖方向

~~~text
前端pages → features → services → contracts
后端routes → service → repository → 数据库驱动
后端controller → contracts
contracts → zod
~~~

禁止：
- contracts导入React、Express、node:fs、数据库连接或环境密钥。
- 前端从backend/src直接导入模型，或者后端从frontend/src取数据。
- UI组件直接执行SQL或拼接业务鉴权逻辑。
- repository反向调用controller。
- auth和review互相导入内部实现形成循环依赖。

跨模块调用通过公开service接口；只有真正共享的协议进入contracts。不要把所有工具函数塞进一个不断膨胀的utils.ts。

### 3.4 当前文件搬迁对照

| 当前文件 | 目标位置 | 搬迁方法 |
| --- | --- | --- |
| frontend/src/App.tsx | app/App.tsx＋pages/＋features/timeline等 | 先逐个抽页面，保持路由和props不变 |
| Graph.tsx | features/people/ | 先拆节点渲染、布局状态、人物侧栏，不同时换图表库 |
| Memory.tsx | features/submissions和features/review | 分开投稿表单、记录列表、审核确认 |
| Session.tsx | features/auth/＋services/http.ts | 保留Context入口，统一请求错误与超时 |
| ui.tsx | components/＋features/sources | Dialog/Empty通用，SourceCard属于史料功能 |
| repository.ts | services/下多文件 | 先保留PlatformRepository接口再移动实现 |
| 两份model.ts | contracts＋业务模块 | Schema/DTO共享；搜索和服务端授权留在业务层 |
| backend/src/app.ts | middleware/＋modules/ | 每次只抽一个Router，原测试保持可运行 |

| 前后端data/fixture | 各mocks和fixtures | 共享样例可从同一测试夹具生成，不复制真实数据 |

## 4 共享协议与构建体系

### 4.1 工作区如何落地

当前frontend和backend各自有package.json、锁文件和pnpm-workspace.yaml；它们还不是统一根工作区。改造时由一名工程负责人集中完成，其他功能分支短时间停止修改依赖。

目标根配置示例：

~~~yaml
# 根pnpm-workspace.yaml，目标配置
packages:
  - frontend
  - backend
  - packages/*
allowBuilds:
  esbuild: true
~~~

~~~json
{
  "name": "fudan-history-platform",
  "private": true,
  "packageManager": "pnpm@11.19.0",
  "engines": { "node": ">=24 <25" },
  "scripts": {
    "build": "pnpm --filter @fudan/contracts build && pnpm --filter fudan-history-backend build && pnpm --filter fudan-history-frontend build",
    "test": "pnpm --filter @fudan/contracts build && pnpm --filter fudan-history-backend test && pnpm --filter fudan-history-frontend test"
  }
}
~~~

以上脚本在contracts包创建后才可用；当前项目仍按两个目录分别执行命令。格式检查和lint等脚本待工具实际安装、配置完成后再加入CI。

迁移步骤：
1. 保留已有备份，记录两个锁文件实际依赖版本。
2. 建立根workspace，将子目录允许执行的依赖安装脚本设置合并到根。
3. 迁移共享包前先保留现有已解析版本，避免重装顺带升级大量依赖。
4. 在迁移分支移除子目录工作区配置与旧锁文件，根目录重新安装生成统一锁文件。
5. 检查根锁文件的importers包含frontend、backend和contracts。
6. 在干净目录重新执行pnpm install --frozen-lockfile，验证构建与测试。
7. 提交源码、根配置和根锁文件；不要提交node_modules。
8. 文档中统一使用根命令，不再混用两套安装方式。

pnpm工作区由根清单定义，内部包用workspace协议声明依赖，可避免意外从远端解析同名包。[官方工作区说明](https://pnpm.io/workspaces)

### 4.2 contracts只放什么

建议分文件：
- common.ts：分页、成功/失败响应、稳定错误码。
- catalog.ts：事件、人物、关系、来源的公开DTO。
- auth.ts：登录请求、当前用户公开信息、角色枚举。
- submission.ts：投稿输入、作者视角记录、公开记忆、审核动作。
- qa.ts：问题输入、引用、证据不足状态、流事件。
- index.ts：明确导出，避免导出全部内部实现。

示例：

~~~typescript
import { z } from 'zod';

export const submissionInputSchema = z.object({
  title: z.string().trim().min(4).max(60),
  year: z.number().int().min(1905),
  body: z.string().trim().min(20).max(2000),
  author: z.string().trim().min(1).max(24),
  consent: z.literal(true)
});

export type SubmissionInput = z.infer<typeof submissionInputSchema>;
~~~

“年份不得晚于服务器当前年份”放在服务用例中按每次请求判断；不要只在模块初始化时计算一次当前年份。字段的基础形状可以共享，动态业务规则和权限必须由服务端执行。

公开、作者、审核员返回对象应分别定义Schema。当前用同一Submission类型、公开响应把reviewNote置空可以保留过渡，但目标应让公开DTO根本没有内部审核字段。

### 4.3 共享包必须能在运行时被导入

TypeScript的类型检查成功，不等于Node运行时能找到共享模块。建议contracts编译为ESM JavaScript与声明文件：

~~~json
{
  "name": "@fudan/contracts",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "scripts": { "build": "tsc -p tsconfig.build.json" }
}
~~~

该包还需声明zod依赖与typescript开发依赖。前后端分别声明：

~~~json
{ "dependencies": { "@fudan/contracts": "workspace:*" } }
~~~

contracts的构建配置使用NodeNext、rootDir=src、outDir=dist、declaration=true。内部相对导入按Node ESM输出要求写.js扩展名。不要以paths别名代替真实包导出配置。[TypeScript模块说明](https://www.typescriptlang.org/docs/handbook/modules/reference.html)

构建顺序：contracts → backend/frontend。开发时先构建contracts，再启动其watch及两端开发服务；修改协议后必须刷新生成产物。

### 4.4 当前后端build的特别问题

当前backend的build是tsc --noEmit，只有类型检查；start通过tsx执行.ts源码。不能写Dockerfile假定已经存在dist/server.js。

分两步调整：
1. 结构拆分阶段保留tsx启动，把命令明确命名为typecheck，避免误解。
2. 正式部署阶段新增tsconfig.build.json，实际输出dist，start改为node dist/server.js；测试仍用tsx。
3. 将当前相对导入中的.ts扩展名调整为匹配NodeNext编译输出的.js，或选择经验证的重写机制，不能直接删除noEmit。
4. fixtures、SQL迁移等非TS资源显式复制到构建产物或独立部署目录。
5. 在没有源目录的临时发布目录测试启动，发现遗漏资源和工作区包依赖。
6. 容器必须包含可解析的contracts产物及运行依赖，不能仅复制backend/dist和假定根node_modules足够。

## 5 前端工程

### 5.1 页面与组件

pages负责路由参数和页面组合；features负责具体交互；components只提供通用表现。首次拆分不改视觉、路由或数据结构，先减少多人修改同一文件的冲突。

建议页面：
- TimelinePage：筛选栏、时期导航、事件列表、详情。
- PeoplePage：关系图、搜索、人物侧栏。
- SourcesPage：来源目录与详情。
- SearchPage：关键词、分类、结果、分页。
- MemoryPage：我的投稿、公开记忆、投稿表单。
- ReviewPage：队列、处理意见、状态冲突提示。
- LoginPage：开发登录；后续正式邮箱/SSO入口。
- QaPage：后续问答、证据查看、取消请求。

组件props以DTO和回调为主。例如EventCard接收event和onOpen，不在内部决定是否访问后端、读localStorage或判断角色。

### 5.2 状态如何分配

| 状态 | 推荐位置 | 例子 |
| --- | --- | --- |
| 临时UI状态 | useState/useReducer | 弹窗开关、关系图坐标、表单输入 |
| 可分享状态 | URL查询参数 | q、period、category、page、record |
| 会话 | SessionProvider或专门的会话查询 | 当前用户、加载中、退出 |
| 服务端数据 | 第一阶段现有hooks；后续TanStack Query | 目录、我的投稿、审核队列 |
| 演示持久化 | 仅demo-repository | 浏览器虚构投稿 |
| 正式持久化 | 后端数据库 | 投稿正文、状态、审核意见 |

不应把同一份服务端投稿同时复制进Context、Zustand和Query缓存。当前规模不必增加Zustand；只有跨页面纯客户端状态确实复杂时再评估。

### 5.3 请求层与缓存

把Session.tsx和repository.ts中的fetch逻辑统一到services/http.ts：
- 统一base URL、credentials、JSON头和X-App-Request。
- GET和短业务写入采用默认超时；AI请求独立配置超时和取消。
- 响应先检查Content-Type和HTTP状态，再校验结构；代理返回HTML错误页时显示连接错误。
- 401触发会话失效事件并引导登录；403显示权限不足，不能无限重试。
- 409刷新记录并保留用户尚未提交的意见。
- POST超时不能直接断言服务端未成功；避免盲目重发，后续用幂等键查状态。

引入TanStack Query后，缓存key至少带用户标识：例如['submissions','mine',userId]。切换账号或退出时清理私有缓存。审核成功后使review、mine和public列表失效，目录有变动时再使catalog失效；不要每次点击都清空全站缓存。[官方缓存失效说明](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation)

### 5.4 时间轴实现

一期继续使用DOM列表，数据量几十条时更容易处理长中文、键盘和手机布局。

实现顺序：
1. 把筛选和分组提取为纯函数并测试组合条件。
2. 查询参数入URL，刷新后恢复筛选；清除筛选统一重置。
3. 详情由稳定ID定位，缺失或下架时显示说明。
4. 日期改为start/end/precision，约年或时期用文字标注，不伪装为精确日期。
5. 多来源叙事先在详情中分栏展示“资料A/资料B”，验证可读性后再做平行泳道。
6. 连续缩放是后续独立任务，需要定义事件聚合规则、密集标签避让与触屏行为，不能仅更换组件名称。
7. 来源标注是可访问链接或按钮，不能只放在鼠标悬停提示中。

### 5.5 人物图实现

当前SVG足以支持小规模演示。抽出：
- useGraphLayout：坐标、缩放、拖动状态。
- GraphEdge：方向、关系类型和选中状态。
- GraphNode：鼠标、触摸、键盘入口。
- PersonPanel：人物详情和关联列表。
- GraphLegend：类别与线型解释。

师生等有方向的关系应显示箭头和文字说明；同窗等对称关系不要误画方向。图中距离、颜色和大小不应暗示未经证实的历史地位或亲疏。

将来使用d3-force时，让D3计算坐标、React负责渲染；不要让两者同时修改同一批DOM。离开页面要停止simulation；布局移动频率高时用ref/requestAnimationFrame限制React更新。节点规模明显扩大后再评估Canvas，不以库名作为性能保证。

### 5.6 表单和可用性

前端使用共享Schema给出及时反馈，后端重复校验。正文始终按文本渲染；加入Markdown或富文本后必须重新评估净化与链接规则。

提交中禁用重复按钮；失败保留输入；清空正文必须在后端确认成功后。保存成功状态用aria-live告知。删除使用确认对话框，区分“撤回展示”和“删除内容”。

至少检查：
- 320px/390px/桌面宽度、200%缩放。
- 仅键盘能到达节点、弹窗和提交按钮。
- 焦点进入弹窗、Escape关闭、关闭后恢复。
- 加载、无数据、错误、成功、无权限五类状态。
- 私有草稿不要未经说明存入共享设备localStorage；若做草稿缓存，提供明确提示和清除机制。

### 5.7 前端验收

真实API模式下浏览、登录、投稿、审核、撤回全链路可运行；demo模式仍可独立展示且明显标记。刷新和复制URL不会破坏筛选或详情。切换账号不会短暂显示上一用户的私有记录。此类数据隔离体验要单独测试，不能只检查服务端403。


## 6 后端工程

### 6.1 请求经过哪些层

处理顺序建议为：请求ID → 安全响应头与请求大小限制 → Origin检查 → 会话解析 → 路由 → 输入校验 → 权限与业务服务 → 数据库 → DTO映射 → 响应。异常统一交给错误中间件，日志包含requestId，客户端不接收SQL、堆栈或凭据。

controller负责HTTP，不负责业务事务。service接收actor和已经校验的输入，不直接依赖req/res，便于命令行导入及测试复用。repository只负责查询，不把“查到了记录”等同于“有权查看”。

错误建议分为ValidationError、UnauthenticatedError、ForbiddenError、NotFoundError、ConflictError和DependencyError，再映射400、401、403、404、409、503。对不应被猜测存在的私有资源，可以统一返回404；团队需在接口文档明确这一政策。

### 6.2 一个审核用例的实现方法

~~~text
reviewService.approve(actor, submissionId, note)
  校验actor具有审核权限
  开启事务
  读取投稿并检查状态、作者与审核政策
  条件更新：WHERE id = ? AND status = 'pending'
  检查受影响行数，0行表示状态冲突
  插入审核日志
  提交事务
  返回最新记录
~~~

当前SQLite使用BEGIN IMMEDIATE同步事务。迁移PostgreSQL后，使用连接池借出同一个client，所有查询、BEGIN、COMMIT、ROLLBACK都在这个client上执行，finally释放；不要把事务中的查询分散到pool.query。[node-postgres事务说明](https://node-postgres.com/features/transactions)

需要“审核后发布正式事件”时，不能仅将投稿状态改为approved后自动当作校史事实。新增编辑核验步骤，把投稿转成带来源的正式条目，并保留submission_id溯源关系。

### 6.3 异步任务与资源管理

导入、OCR、分块和Embedding不要在数据库事务中等待外部模型。推荐：
1. 短事务记录任务及输入版本。
2. worker领取任务，设置租约、尝试次数、运行状态。
3. 事务外调用外部服务。
4. 写回前确认资料版本和权限仍有效。
5. 幂等写入结果，标记成功；失败记录可重试原因。
6. 超时任务可重新领取，唯一约束防止重复产物。

初期可以用命令行逐批执行任务；需要持续后台处理时再建立job表和独立worker进程，不必立即引入Redis。任务状态至少有queued/running/succeeded/failed/cancelled；要能识别永久失败与临时限流。

服务关闭时停止接收新请求，允许短请求完成，取消模型调用并关闭数据库连接。进程重启后要能恢复未完成任务，不能依赖内存数组保存队列。

### 6.4 配置与依赖注入

在启动时一次性解析环境变量，错误就停止启动。布尔值不要使用Boolean("false")；端口、超时、配额必须校验范围。服务工厂接收数据库、时钟、模型适配器等依赖，以便测试替换，不要在每个模块顶层创建全局连接。

日志记录事件和结果，例如review.completed、qa.timeout；默认不记录密码、Cookie、验证码、完整投稿正文或完整提问。需要分析问题时保留脱敏样本，并约定访问权限与保留期。

## 7 数据模型与数据库迁移

### 7.1 当前与目标的差别

现有users、sessions、catalog_items、submissions、review_logs支持原型。catalog_items的JSON模式便于快速开发，但复杂关联、资料撤回、按来源统计和历史版本查询会逐渐困难。

正式数据阶段将目录拆成关系表；不要把全部历史JSON丢给LLM代替结构化数据。建议核心模型如下：

| 表 | 关键字段 | 约束和用途 |
| --- | --- | --- |
| users | id、email、display_name、status | email规范化唯一；角色由后台授权 |
| user_roles | user_id、role | 联合唯一；小团队也可暂保留单role |
| sessions | token_hash、user_id、expires_at | token摘要唯一；用户及过期时间索引 |
| people | id、name、summary、publication_status | 稳定ID，不用姓名当主键 |
| person_aliases | person_id、alias、normalized_alias | 支持曾用名、繁简及别称，保留原文 |
| events | id、title、start_date、end_date、date_precision、summary | 时间精度year/month/day/range/unknown |
| event_people | event_id、person_id、participation_role | 多对多；描述参与方式 |
| relations | id、from_person_id、to_person_id、type、direction、description | 类型受控；不强行将所有关系双向化 |
| sources | id、title、creator、publication、locator、rights_status、visibility、ai_processing_allowed | 来源、展示许可与AI处理许可分开 |
| source_versions | id、source_id、version、content_hash、storage_key、status | 原文更新生成新版本，禁止悄悄覆盖 |
| event_citations | event_id、source_version_id、page_or_locator、excerpt | 支撑具体事件 |
| person_citations | person_id、source_version_id、page_or_locator、excerpt | 支撑人物叙述 |
| relation_citations | relation_id、source_version_id、page_or_locator、excerpt | 支撑关系断言 |
| submissions | id、owner_id、title、body、status、version、created_at、updated_at | 内容不混入正式目录 |
| review_logs | id、submission_id、actor_id、action、note、created_at | 审核变更可追溯 |
| import_batches | id、input_hash、operator_id、status、report_key | 记录导入批次与校验结果 |
| document_chunks | id、source_version_id、ordinal、text、locator、chunk_hash | RAG分块及原文定位 |
| chunk_embeddings | chunk_id、model_id、dimension、embedding_version、vector | 模型版本与维度严格匹配 |
| jobs | id、kind、input_version、status、attempts、lease_until | 后续后台任务 |

引用表分别建表，比通用target_type/target_id更容易用数据库外键保证完整性。某些来源只支撑一句话而非整篇简介时，增加claim记录，再把引用关联到claim；这一扩展在真实编辑需求出现后实施。

### 7.2 日期、标识和历史争议

- ID沿用现有稳定字符串，迁移时建立映射；不要为了统一UUID打断已保存链接。新记录可用UUID。
- 系统时间用UTC存储、界面按上海时区显示；PostgreSQL使用timestamptz。
- 历史时间不是系统时间。仅知年份时保存精度信息，显示“约某年”；未知年份允许为空。不要把1月1日当作确定史实展示。
- 人名同名不自动合并；别名匹配只给候选，由内容组核验。
- 冲突史料保留不同主张及引用，在展示和问答中说明分歧，不能用覆盖更新抹掉争议。
- 图上x/y属于布局配置，不应成为人物史料的固有属性。

### 7.3 索引和并发

先按真实查询建立索引：投稿(owner_id, created_at)、投稿(status, created_at)、事件时间、关联表外键、来源版本(source_id, version)唯一、分块(source_version_id, ordinal)唯一。索引过多会拖慢导入，应看执行计划和实际数据量。

编辑接口加入version实现乐观锁：UPDATE ... WHERE id=$1 AND version=$2，并将version加一；受影响0行返回409。审核状态机同样使用条件更新，不能先查状态、事务外再无条件覆盖。

### 7.4 迁移方法

当前启动代码中的CREATE TABLE IF NOT EXISTS和PRAGMA user_version=1不是完整迁移系统。正式引入：
- 编号不可变迁移，例如0001_initial.sql、0002_source_versions.sql。
- schema_migrations记录版本、校验和、执行时间。
- 单独迁移命令，使用部署锁防止多个实例同时迁移。
- 已执行迁移不编辑；新问题追加迁移。
- 先增加兼容字段和回填，再切换代码，最后删除旧字段。
- 大规模回填分批执行，避免持有过长事务。

SQLite转PostgreSQL过程：
1. 备份并试恢复；暂停写入或设计明确增量切换机制，一期选择短暂停写。
2. 导出为中间JSON，验证计数、引用、状态、时间和账号映射。
3. 在空PostgreSQL运行迁移并导入。
4. 比较实体数量、关系完整性、内容摘要；抽查中文与换行。
5. 跑权限、审核、搜索、删除回归；不要只验证能连接。
6. 切换应用配置，验证后解除暂停写入。
7. 保留旧库只读备份。发生新写入后不能直接切回旧库，否则会丢失新数据，需回放或反向同步。

## 8 接口规范与完整业务流程

### 8.1 保持当前兼容，再逐步扩展

当前成功格式是{code:0,message:"ok",data:...}，错误使用HTTP错误状态及对应code。当前写操作有返回data:null的情况；前端依赖JSON解析，不能未经同步就改成204。

| 当前接口 | 作用 | 规划处理 |
| --- | --- | --- |
| GET /api/health | 开发服务状态 | 保留存活检查；新增真实依赖就绪检查 |
| GET /api/catalog | 公开目录 | 小数据保留；规模扩大后拆分页列表 |
| GET /api/search?q= | 关键词搜索 | 前端接入，逐步添加筛选与分页 |
| POST /api/auth/login | 本地开发账号登录 | 正式身份接入前只用于受控开发 |
| GET /api/auth/me | 当前会话 | 返回最小公开用户信息 |
| POST /api/auth/logout | 注销 | 同步清理前端私有缓存 |
| GET /api/submissions?scope=mine/review/public | 投稿列表 | 保持服务端scope授权 |
| POST /api/submissions | 创建投稿 | 服务端决定owner和pending状态 |
| POST /api/submissions/:id/:action | approve/reject/withdraw | 状态冲突返回409 |
| DELETE /api/submissions/:id | 作者删除 | 处理正文、日志、索引与备份政策 |
| POST /api/qa/retrieve | 关键词证据检索 | 保留为可诊断入口，不冒充生成问答 |

计划新增而非当前可用：
- GET /api/events、/api/people、/api/sources：游标分页和详情。
- POST /api/auth/email/start、/verify：若选择邮箱验证码。
- POST /api/admin/imports/validate、/commit：导入预检和发布。
- POST /api/qa/ask：一次性RAG问答。
- POST /api/qa/stream：后续流式问答。

### 8.2 接口设计方法

每个接口必须说明：角色、输入Schema、输出Schema、状态码、分页、幂等性、示例及失败情况。使用OpenAPI描述，与contracts通过生成或契约测试保持一致；先选一个主源，避免手工维护两份互相矛盾的定义。

列表分页建议cursor＋limit，固定排序键如(created_at,id)；限制limit上限。返回items、nextCursor、hasMore，确需总数时再计算total。游标不能替代权限，后端每页都重新应用范围条件。

客户端不能传入可信的owner_id、reviewer_id或role。对于无法修改的字段，可以严格拒绝未知字段，或明确丢弃；当前行为与目标行为变化必须更新测试。

### 8.3 完整业务流程

~~~text
成员登录
  → 提交正文与展示同意
  → 服务端校验并记为pending
  → 作者可查看自己的投稿
  → 审核员查看队列并处理
  → approved才进入公开记忆
  → 作者withdraw后立即退出公开展示
  → 搜索/缓存/问答同步失效
~~~

“审核通过的个人回忆”与“核实后的校史事实”应有明确标识。投稿如果要进入AI知识库，还需要资料核验、单独的处理许可和来源定位。

## 9 登录授权与内容审核

### 9.1 正式身份的两条路径

**可取得学校对接授权时**：由负责人联系学校确认SSO协议、测试环境和属性字段；按对方OIDC/SAML等实际协议接入。不能仅凭学校名称假设公开存在可用SSO。

**暂时无法接入SSO时**：实现邮箱验证码。邮箱域名由学校确认后配置；验证码随机生成、只存摘要、短期有效、单次使用，限制发送与验证次数，并使用统一提示避免账号枚举。成功后创建服务端会话。真实邮件发送需要邮件服务凭据和投递测试，不是前端校验邮箱后直接放行。

注册默认为member；reviewer/admin由受控操作授予并记审计。不要允许注册表单选择审核员。

### 9.2 会话与请求防护

继续使用随机会话标识，数据库只保存摘要。生产启用HTTPS和Secure Cookie，保留HttpOnly与合适的SameSite。登录成功轮换会话，退出删除服务端记录，停用账号可撤销其全部会话。

当前Origin白名单、JSON写请求和X-App-Request用于开发请求约束。正式部署仍需设计完整CSRF策略；若接入跨站SSO或跨域前后端，重新验证Cookie和回调行为，必要时使用服务端校验的CSRF令牌。不能把CORS或SameSite单独当作全部防护。[OWASP CSRF说明](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

当前Cookie的Secure=false和拒绝production启动都是原型边界。上线前按完整生产清单改造，不能仅删除启动保护。

### 9.3 权限矩阵

| 行为 | 游客 | 成员 | 审核员 | 管理员（计划） |
| --- | --- | --- | --- | --- |
| 浏览已公开目录/记忆 | 是 | 是 | 是 | 是 |
| 创建投稿 | 否 | 是 | 是 | 是 |
| 查看自己未公开投稿 | 否 | 是 | 是 | 是 |
| 查看待审核内容 | 否 | 否 | 是 | 按职责 |
| 审核他人投稿 | 否 | 否 | 是 | 按职责 |
| 撤回/删除作者内容 | 否 | 本人 | 本人 | 另设有审计的管理流程 |
| 修改来源许可/发布史料 | 否 | 否 | 非默认 | 有单独授权 |
| 管理角色 | 否 | 否 | 否 | 是 |

计划禁止审核自己的投稿；这与当前实现不同，需增加服务端政策和测试。人数少时由另一审核员处理，不通过前端隐藏按钮代替规则。

### 9.4 撤回与删除

撤回改变发布状态，保留作者可见记录；删除清除约定的业务内容。已生成的搜索索引、Embedding、问答缓存、会话历史和文件副本都需要纳入处理范围。

现有删除已经匿名化相关审核日志，但备份可能保留旧内容。制定备份保留期与恢复后重新应用删除/撤回清单的流程，不能承诺点击删除后所有离线备份立即消失。日志只保留必要操作证据，避免重新复制正文。


## 10 史料采集与数据流水线

### 10.1 资料先登记，再加工

每份资料登记source_id、名称、作者/编者、版本、出版或形成时间、馆藏/公开链接、页码、采集人、采集日期、许可依据、展示范围、是否允许外部AI处理。区分资料可以在网站展示、可以下载原件、可以发送模型三种权限。

真实原始文件放受控存储，Git只保存模板、虚构样例、转换脚本和不含敏感内容的校验规则。授权记录也可能含个人信息，应限制访问。文件命名使用ID和版本，不把身份证号或私密姓名写入路径。

### 10.2 提取与人工核验

推荐工具分工：
- Python辅助数据处理，使用独立虚拟环境与锁定依赖。
- DOCX使用python-docx提取段落和表格，同时保留标题层级；注意脚注、文本框不一定被普通遍历覆盖。
- 有文字层PDF先提取文本与页码；扫描件再采用经验证的OCR工具，例如PaddleOCR。OCR版本、模型文件和运行资源先做小样本试验再固定。
- 表格资料使用CSV/JSON作为交换格式，明确UTF-8、日期格式和空值表达。
- 图像和原件记录SHA-256用于去重与核对，不以文件名判断重复。

OCR最容易误识别人名、年代、旧字体与双栏顺序。内容组逐页核对关键断言，不能把OCR输出自动标为已核实。中文简繁转换用于匹配辅助，保留原文版本，避免改变历史名称。

### 10.3 导入分为预检与提交

~~~text
raw原件
  → 提取文本与页码
  → staging待校对数据
  → 内容组校对/许可复核
  → Schema、引用、ID、日期校验
  → 生成预检报告与差异
  → 授权人员确认批次
  → 事务写入正式表
  → 重建受影响搜索/向量索引
~~~

预检报告至少列出新增、更新、冲突、缺失引用、重复ID、异常年份、无许可记录。发现错误时整批禁止发布；支持“只校验”命令，不得默认写库。

提交时记录输入摘要和批次ID。同一批次重复执行应幂等；禁止使用“清空全库再seed”更新真实资料。来源版本更改后，旧引用保留历史定位，新版本经过复核才启用。当前首次启动seed只是演示初始化，不能承担正式导入任务。

### 10.4 文件存储

早期受控本机目录可用；正式部署采用持久卷或对象存储，数据库保存storage_key而非用户给出的路径。上传限制文件类型、大小、数量和真实文件签名，生成服务端文件名。下载时重新判断权限，私有文件不得放frontend/public。

存储、数据库和索引的备份版本需要能对应。仅备份数据库而丢失其引用的原始文件，无法恢复史料系统。

## 11 搜索与RAG

### 11.1 先改善普通搜索

当前检索以字符串匹配为主，没有分词和向量。优先做：
1. 前端调用后端搜索，统一权限、筛选和排序。
2. 支持姓名/别名、标题、正文和来源字段；命中标题、姓名优先。
3. 明确中文标点、空格、繁简及别名归一化策略。
4. 小数据量可采用参数化LIKE/ILIKE与别名匹配，注意转义用户的%和_。
5. 数据增加后，根据中文查询集选择经验证的分词或检索方案；PostgreSQL默认全文检索配置不能直接假定适合中文。
6. 用真实查询测相关性和耗时，再决定是否需要额外搜索服务。

关键词搜索是独立可用能力，也是RAG的候选召回来源。

### 11.2 RAG的固定流程

~~~mermaid
flowchart LR
  Q[用户问题] --> A[身份与权限范围]
  A --> R[关键词与向量候选]
  R --> F[当前发布状态与许可过滤]
  F --> D[去重和排序]
  D --> E{证据是否足够}
  E -->|不足| N[说明缺失资料]
  E -->|足够| L[模型仅根据给定证据回答]
  L --> V[引用与输出校验]
  V --> O[回答和可点击出处]
~~~

RAG不是把全部资料拼入提示词。它要解决“选出相关且有权使用的证据”，并让每个重要历史断言可追溯。

### 11.3 分块与Embedding

初始可按标题、段落、页码切块，以约400—800个中文字符为实验起点，重叠50—100字符；最终按所选模型token限制与评测调整。字符数不等于token数。不要把表格行、引用、跨页姓名说明截断得无法理解。

每块保存：source_version_id、页码/段落定位、标题路径、正文、chunk_hash、分块器版本、审核状态。许可判断仍关联当前来源记录，不把旧的许可快照当作永久授权。

Embedding适配器约定：
- embedDocuments(texts)用于建库，embedQuery(question)用于提问；遵守模型是否区分任务前缀的要求。
- 明确model_id、维度、批量上限、超时和重试策略。
- 重试只针对限流和暂时网络问题，使用退避和上限。
- 建库记录输入摘要及模型版本，避免重复付费。
- 不同模型生成的向量不能混在同一相似度空间；切换模型重建索引，验证后切流。

维度不能在设计阶段随意写死为1536等数值。确定实际模型后，再创建匹配的vector(d)字段。

### 11.4 PostgreSQL与pgvector

由部署负责人安装与数据库版本匹配的pgvector扩展。先用精确向量检索验证结果，数据和延迟确有需要后再增加HNSW等近似索引。索引度量与查询距离算子必须匹配；近似检索结合权限过滤时可能返回不足候选，需要验证查询策略。[pgvector官方说明](https://github.com/pgvector/pgvector)

示意SQL，仅在pgvector及对应字段已经部署后适用：

~~~sql
SELECT c.id, c.text, c.locator, s.id AS source_id
FROM chunk_embeddings e
JOIN document_chunks c ON c.id = e.chunk_id
JOIN source_versions v ON v.id = c.source_version_id
JOIN sources s ON s.id = v.source_id
WHERE s.visibility = 'public'
  AND s.ai_processing_allowed = true
  AND v.status = 'published'
  AND e.model_id = $2
ORDER BY e.vector <=> $1::vector
LIMIT $3;
~~~

实际代码还要校验模型维度、候选上限和当前用户可见范围。私有语料先通过权限条件限制候选，绝不能将未经授权的候选先发给外部重排模型，再做权限过滤。

### 11.5 混合召回与重排

建议起步参数：关键词与向量各召回20条，去重后选6—8块进入上下文。这些是实验起点，不是质量保证。

两路分数尺度不同，不直接相加。可用RRF：每个候选按各路排名累加1/(k+rank)，k作为可调参数。需要重排时接入独立reranker适配器，比较增加的准确率、费用和延迟；先用公开可处理语料验证。

按来源去重，避免同一段重叠文本占满上下文。必要时补取相邻段落，但仍受token预算和权限限制。

### 11.6 生成与引用校验

模型输入包含任务说明、问题和编号证据，不包含不必要的用户邮箱、会话凭据或未审核投稿。提示词要求：只依据给定证据；不足就说明；区分史料冲突；引用给定证据ID。

返回建议结构：

~~~json
{
  "answer": "依据已提供资料形成的回答。",
  "citations": [
    { "chunkId": "chunk-001", "sourceId": "source-001", "locator": "第12页" }
  ],
  "insufficientEvidence": false,
  "requestId": "request-001"
}
~~~

上面ID和正文只是格式示例。模型输出的标题、页码、链接均不能直接信任；服务端以实际检索记录重建引用元数据，拒绝未知chunkId。引用存在不代表断言被支持，因此还要人工评测断言与证据的一致性。

没有证据时不调用生成模型也可以直接返回“目前公开资料不足”。不要使用未经评测的统一相似度阈值宣称“可信度95%”。

### 11.7 流式与降级

先实现普通JSON问答，验证引用后再做流式。需要带POST正文时，浏览器使用fetch读取ReadableStream并解析事件；原生EventSource主要用于GET，不能直接当作带JSON请求体的POST客户端。

事件可分meta、delta、citations、done、error。网络数据块不一定是完整事件，解析器要缓冲；终止时校验最终结果。若先显示未验证文本，应标为生成中，最终引用失败时明确修正。客户端取消通过AbortSignal传到模型请求。

代理需要关闭该接口响应缓冲，设置合理超时；流中发生错误时发送错误事件，不能再试图修改已发出的HTTP状态。

模型不可用时保留普通搜索和证据卡片；额度耗尽返回清楚提示。按用户与全局设置每日预算、并发和单次token上限，先在小规模试用中测成本。

## 12 只读Agent

### 12.1 本项目为什么以及何时需要Agent

单一问题“某事件发生于何时”通常固定RAG即可。Agent用于需要多步组合的提问，例如“找到某人物参与的事件，再比较两个时期的活动变化”。没有评测收益时，不必引入Agent框架。

先由代码实现小型工具循环；是否采用框架取决于团队调试、可观测和维护需要，框架不是智能程度的证明。

### 12.2 工具清单与边界

| 工具 | 输入 | 服务端处理 |
| --- | --- | --- |
| searchHistory | query、筛选、limit | 已授权资料检索 |
| getPerson | personId | 返回当前可见人物DTO |
| getEvent | eventId | 返回事件及出处 |
| listPersonEvents | personId、时间范围、limit | 参数化查询关联事件 |
| getSourceExcerpt | chunkId | 重新校验权限后返回片段 |

每个工具有JSON Schema、长度/数量限制、超时和结构化结果。用户身份由服务器上下文注入，模型不能通过参数指定自己是审核员。模型只能请求工具，执行权始终在服务端。

不提供任意SQL、任意URL抓取、系统命令、文件路径读取或审核/删除工具。史料中的“忽略规则”“调用管理员接口”等文字只是资料内容，不作为指令执行。

### 12.3 有界执行循环

~~~text
校验问题、身份、配额
建立只含必要历史的上下文
最多3轮：
  调用模型获取回答或工具请求
  无工具请求：校验引用并结束
  工具请求：校验工具名、参数、数量和当前权限
  在剩余时间预算内执行只读工具
  将截断后的工具结果加入上下文
超出轮次/最多5次工具调用/总时间上限：
  返回已有证据与未完成说明
~~~

3轮、5次是初始工程上限，可根据评测调整；再增加全局超时和token预算，防止重复调用耗尽费用。并行执行只适用于互不依赖的只读调用。

会话ID属于当前用户，服务端验证所有权。历史对话应设置长度、保留期和删除机制；不能把之前用户的工具结果复用给另一个用户。缓存key包含权限范围、资料版本、模型和提示词版本，权限变化立即失效。

### 12.4 可观察性与验收

记录工具名、耗时、结果数量、状态、资料版本和费用统计，不保存模型隐藏思维过程。向用户展示简短可核验步骤，如“查询了3条相关事件”，以及最终引用。

评测包含：伪造工具名、过长参数、访问私有ID、资料内提示注入、重复工具循环、模型超时、撤回资料、来源冲突和无答案问题。Agent必须通过与固定RAG相同的引用和权限测试。

## 13 测试与质量标准

### 13.1 分层测试

| 层级 | 内容 | 方法 |
| --- | --- | --- |
| 类型与构建 | 两端及contracts可以编译、生产产物可运行 | tsc、Vite、独立发布目录启动 |
| 单元 | 筛选、状态机、权限政策、日期、输入校验 | 保留现有node:test体系，按需求增加 |
| 接口集成 | 登录、所有权、审核、冲突、删除、错误码 | 临时数据库＋真实HTTP应用 |
| 数据库 | 迁移、外键、事务回滚、并发审核 | 独立测试SQLite/目标PostgreSQL |
| 前端交互 | 表单失败保留、对话框焦点、401和409 | 需要时引入组件测试工具 |
| 端到端 | 成员A/B隔离、审核员、撤回、公开消失 | Playwright，通过公开UI完成 |
| 数据质量 | 引用缺失、重复ID、非法日期、无许可 | 导入预检脚本和人工复核 |
| RAG/Agent | 召回、引用、拒答、权限、成本 | 固定问答集＋人工标注 |

现有本地.qa脚本含机器相关路径，不应原样当作可移植CI。提取成标准测试目录，服务地址与凭据通过测试配置注入，测试账号在临时数据库生成。

### 13.2 必须保护的回归场景

- 成员A无法读取或修改B的私有投稿，即使直接调用接口。
- 两名审核员同时处理时只允许一个状态迁移成功。
- 数据更新失败时审核日志也回滚，不出现半成功。
- 撤回或来源许可收回后，页面、搜索和问答都不再暴露相关内容。
- 注销/账号切换后浏览器不显示旧用户缓存。
- 数据库恢复后，删除清单重新应用，避免旧内容复活。
- 模型不可用时基础浏览和投稿仍能使用。
- 编译产物在不依赖源码目录的环境中能够启动。

### 13.3 RAG评测方法

由内容组和AI组共同建立首批约50道问题：事实、人物关系、比较、资料冲突、无答案、越权诱导各占一定比例。每题保存允许使用的证据和参考要点，不要求回答逐字一致。

分别统计：
- Recall@k：应命中的证据是否进入候选。
- 引用有效率：引用是否真实存在、可定位、当前可见。
- 断言支持率：回答中的事实是否被所引证据支持。
- 无答案识别：缺少证据时是否恰当拒答。
- 延迟与单次费用：记录P50/P95和异常比例。
- 隐私与权限：越权测试必须全部通过。

首批样本少，不能用一个总体百分比证明上线可靠。质量阈值由团队在真实资料集上制定；结构与权限约束则应作为必须通过的门槛。

### 13.4 性能与容量

先约定并发人数、目录规模、文档页数、提问频率，再在接近部署配置的机器上测量。可提出“普通页面接口P95小于500ms”等目标，但本文没有实测支持，不作为当前承诺。

负载测试不要直接使用付费模型无限发请求；用模拟适配器测应用并发，再以有限真实请求测模型延迟与费用。


## 14 代码协作与持续集成

### 14.1 仓库与分支

采用一个远程仓库，main保持可运行。每个任务从最新main创建短分支，如feat/source-import、fix/submission-conflict、docs/restore-guide。通过PR合并，由至少一名相关同学审查。平台是否支持分支保护、团队权限和配额，应在选定Git托管服务后确认。

任务卡写清：背景、范围、负责人与审查人、接口影响、验收步骤。一个PR应能独立验证；目录重构和功能开发分开提交。接口变更先讨论contracts，再并行实现前后端。

前后端约定示例响应后，前端可用demo适配器开发；真实联调必须验证失败状态与权限，不只看成功截图。

### 14.2 减少冲突的方法

- 每个模块明确主维护人；App.tsx、app.ts只做装配，修改时间提前沟通。
- contracts和锁文件变更指定一人协调，不以手动删冲突行方式修锁文件。
- 遇到锁文件冲突，先合并package.json依赖意图，再由固定pnpm重新生成并验证。
- 二进制DOCX不适合逐行合并，规划和接口使用Markdown；原始计划书保留只读版本。
- 数据ID和Schema变更随PR提供兼容策略及示例。
- 不提交node_modules、dist、本地数据库、真实史料、.env、账号文件和调试截图。
- 密钥已经进入Git时，删除文件不等于消除泄漏，需轮换并处理历史。

PR模板建议包含“改动解决什么问题、影响哪些模块、怎样验证、是否涉及数据迁移、界面截图、剩余限制”。CODEOWNERS仅辅助指定审查人，实际强制审查需要仓库规则配置。

### 14.3 CI分两个阶段

**当前双目录阶段**，命令顺序为：

~~~powershell
pnpm -C frontend install --frozen-lockfile
pnpm -C backend install --frozen-lockfile
pnpm -C frontend test
pnpm -C backend test
pnpm -C frontend build
pnpm -C backend build
~~~

注意最后一个命令目前仅做类型检查。以上是现状命令清单，本次文档工作未重新运行整套测试。

**统一工作区后**：一次根安装，先构建contracts，再分别测试和构建。下例是迁移完成后的目标流程；Action主版本为配置示例，落地前核对并固定审核过的提交SHA。

~~~yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 11.19.0
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm test
      - run: pnpm build
~~~

不要将target结构的命令直接粘进当前项目。Node内置SQLite及本机/CI系统差异要通过实际CI验证。端到端测试在基础CI稳定后加入，失败保存报告，避免把用户数据作为测试附件。

PR触发与权限配置参考[GitHub Actions官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。外部PR测试不提供生产密钥，也不运行自动部署生产。

### 14.4 文档维护责任

API变更同步docs/api；字段变更同步数据字典；新依赖和架构决定写ADR；部署流程同步runbook。ADR简写四项：问题、选择、理由、后果。每次里程碑由负责人检查文档中的“当前状态”，避免规划被误认为已交付。

## 15 部署配置与运维

### 15.1 三类环境

| 环境 | 数据 | 目的 | 访问 |
| --- | --- | --- | --- |
| 本地开发 | 虚构fixtures＋本机测试账号 | 开发与调试 | 127.0.0.1 |
| 测试/预发布 | 脱敏或获准的小规模资料 | 联调、迁移和恢复演练 | 团队受控 |
| 正式 | 已核准资料与真实账号 | 实际服务 | HTTPS与正式权限 |

环境使用不同数据库、密钥和存储路径。测试不得连接正式数据库；应用启动输出环境与非敏感连接目标以便核对，禁止打印连接密码。

### 15.2 配置清单

| 变量 | 阶段 | 说明 |
| --- | --- | --- |
| VITE_DATA_MODE | 当前 | demo或api；构建进前端 |
| VITE_API_BASE_URL | 当前 | 推荐同源/api |
| PORT | 当前 | 后端端口，默认按现有配置 |
| DB_PATH | 当前SQLite | 持久数据库路径 |
| ALLOWED_ORIGINS | 当前 | 精确来源列表 |
| NODE_ENV | 当前/目标 | 当前server拒绝production |
| HOST | 计划新增 | 本地127.0.0.1；容器按设计监听0.0.0.0 |
| DATABASE_URL | PostgreSQL阶段 | 仅后端读取，不暴露到Vite |
| SESSION_TTL_SECONDS | 正式身份阶段 | 会话期限及测试覆盖 |
| SMTP_*或SSO_* | 正式身份阶段 | 依据选定服务确定具体字段 |
| EMBEDDING_MODEL、EMBEDDING_DIMENSION | RAG阶段 | 与索引版本一致 |
| MODEL_API_KEY、MODEL_BASE_URL | RAG阶段 | 服务端保管，按供应商适配 |
| QA_MAX_TOKENS、QA_TIMEOUT_MS | RAG阶段 | 校验上限并提供降级 |
| LOG_LEVEL | 运维阶段 | 避免生产调试日志包含正文 |

这些计划变量尚未全部被当前代码读取。所有VITE_变量都应视为公开构建信息，不能存放模型密钥或数据库密码。.env.example只放占位值，实际密钥通过部署环境注入。

### 15.3 发布步骤

1. CI通过，记录提交号、依赖锁文件及迁移版本。
2. 生成前端静态产物、后端真实JS产物和contracts运行包。
3. 将后端开发seed改为显式开发命令；正式环境不能自动创建随机开发账号。
4. 在预发布恢复备份、执行迁移和完整冒烟测试。
5. 构建容器，应用使用非root用户；数据放持久卷，不存容器临时层。
6. 配置Nginx提供静态资源与/api同源代理，HTTPS证书自动续期并监测。
7. 数据库不直接暴露到公网；备份通道单独配置。
8. 设置就绪检查后启动，检查登录、投稿、审核、来源与检索。
9. 记录发布结果和回退条件。

当前服务监听127.0.0.1，放入容器后其他容器无法按普通网络方式连接它；需要有意识地改为容器内0.0.0.0，并通过端口映射和网络限制对外范围。

Compose启动顺序不等于服务已经可用；使用healthcheck及service_healthy依赖，同时应用自身应处理数据库短暂不可用。[Docker Compose启动说明](https://docs.docker.com/compose/how-tos/startup-order/)

### 15.4 代理与会话

使用Nginx后正确配置Express trust proxy，按真实代理链确定可信地址/跳数；不要不加区分地设置true。否则客户端IP、协议判断和限流可能失真。[Express代理说明](https://expressjs.com/en/guide/behind-proxies/)

当前按进程内存和IP限流，在多个实例下不共享，重启也会清空。单实例试点可保留受控配置；正式扩大后使用共享限流存储或网关，同时按账号限制昂贵AI请求。校园网络可能多人共用出口IP，不能仅依赖IP封禁。

HashRouter可继续使用；改为BrowserRouter时，Nginx要提供前端路由回退，但/api错误不能回退为index.html。

### 15.5 备份、恢复与监控

当前SQLite通过项目backup脚本使用在线备份能力；WAL运行时不要只复制主.sqlite文件。正式PostgreSQL采用数据库备份工具，视恢复目标增加连续归档方案；文件存储也独立备份。

建议先提出试点目标：每日备份、可恢复最近24小时内数据、4小时内恢复服务。RPO/RTO只是待演练验证的目标，要由实际使用需求确认。

恢复演练：
1. 在隔离环境恢复数据库与匹配文件。
2. 验证计数、关键引用和授权状态。
3. 应用备份之后的删除/撤回清单。
4. 使旧会话失效，必要时轮换密钥。
5. 清理或重建搜索、向量索引和缓存。
6. 跑登录、隔离、审核、出处与问答冒烟。
7. 记录实际恢复耗时和失败步骤。

监控至少覆盖5xx比例、P95延迟、数据库空间、备份新鲜度、任务失败、模型额度和引用校验失败。现有/api/health不能证明数据库及外部模型都可用；新增ready检查并控制检查成本，不必每次探针调用付费模型。

## 19 术语与官方参考

### 19.1 常用术语

| 术语 | 本项目中的含义 |
| --- | --- |
| Monorepo/单仓库 | 前后端与共享协议在同一Git仓库协作 |
| 模块化单体 | 一个后端应用，内部按业务划清模块 |

| Migration | 有编号、可追踪的数据库结构变更 |
| RAG | 先检索证据，再结合证据生成回答 |
| Embedding | 将文本转换为用于相似度检索的数值向量 |
| Agent | 模型在服务端约束下选择并调用工具的流程 |
| 幂等 | 同一操作重复执行不会产生额外重复结果 |
| RPO/RTO | 可接受数据损失窗口/服务恢复目标时间 |
| ADR | 记录架构选择及其理由的短文档 |
