# 校史平台接入与协作手册

这版已经完成可运行的一期前端原型。下一步应先打通经过考证的只读数据，再接身份认证和投稿审核；AI、地图与社群延后。无需一次实现计划书第四章全部功能。

## 1 先演示再分工

按README启动，实际走完时间轴→人物→出处，以及投稿→审核→展示→撤回。前端3人可以分别接手：
- 页面、导航、响应式和搜索：App.tsx、ui.tsx、styles.css。
- 时间轴与关系图：App.tsx的Timeline、Graph.tsx，未来扩展连续缩放与力导向。
- 投稿和审核：Memory.tsx，与后端共同维护repository.ts和model.ts。

修改接口前由前后端共同确认API约定，避免各自改字段。每个任务定义输入、页面状态、完成标准；代码合并前至少另一人检查。优先修复无法浏览、无法投稿、误公开和丢数据问题。

## 2 内容组怎么接真实资料

第一批建议准备10个事件、5个人物和5条关系，而非立刻追求全部数量。
1. 为每份材料分配稳定ID；登记原文标题、机构/作者、日期、页码/档号、链接。
2. 分开记录“材料可取得”和“允许公开哪些内容”。不可仅因网页公开就认定可以全文转载。
3. 把事件概述、原文摘录、个人解释分开；没有精确日期时保留“约”“时间范围”等信息。
4. 关系按具体依据认定，不能仅凭同年在校推定同窗或师生。
5. 两人复核事实与关联，再决定是否公开。展示元数据也应检查是否含个人信息。
6. 正式数据demo=false；演示资料不可混入真实馆藏目录。保留登记表作为原始依据。
7. 后端只返回允许公开的数据；有一个公开来源不代表该条目的全部正文都已得到授权。

原型内置数据全部在src/data.ts，均为虚构。临时演示可修改此文件，但正式流程应走数据导入与审核，不依赖前端开发者手工改史料。

建议史料登记表列：
id、title、kind、creator、dateText、archiveId、page、url、excerpt、authorizationStatus、allowedScope、reviewer1、reviewer2、reviewedAt、notes。

## 3 后端组怎么完成

建议一个Node.js + TypeScript后端、一个PostgreSQL数据库先起步。NestJS或Express由团队熟悉程度决定；目前无需Redis、微服务、图数据库或向量库。

最短实现顺序：
1. 建库迁移和目录导入，实现GET /catalog，联通只读页面。
2. 实现学校邮箱验证码登录和会话；前端补登录页、退出、登录状态。
3. 实现提交、mine列表、所有权校验。
4. 由管理员在服务端分配审核员角色，实现审核列表及审核操作。
5. 实现public列表、撤回、删除；保证撤回立即从公开返回中消失。
6. 增加限流、审计日志、备份、异常处理，再扩大试用。

[API约定](API约定.md)与现有HttpRepository逐项对应。任何真实权限校验都必须在服务器执行。前端的原型审核入口不承担鉴权职责。

数据库可按下表建立，由后端用迁移管理：

| 表 | 关键字段 | 关键约束 |
| --- | --- | --- |
| users | id、email、display_name、role、verified_at | 邮箱唯一；角色member/reviewer/admin；邮箱验证后才可投稿 |
| sessions | id_hash、user_id、expires_at | 存会话摘要、到期清理，撤销可立即生效 |
| sources | id、title、kind、citation、excerpt、url、authorization_status、allowed_scope、publication_status | 授权和发布状态分别管理 |
| events | id、year、date_text、title、category、summary、content、place、publication_status | year用于索引；date_text保留不确定性 |
| people | id、name、role、years、summary、publication_status | 同名人物不要自动合并 |
| relations | id、source_person_id、target_person_id、type、date_text | 两端人物外键，禁止自连接，避免重复关系 |
| event_sources / person_sources / relation_sources | 实体ID、source_id | 外键和组合唯一索引 |
| event_people | event_id、person_id | 外键和组合唯一索引 |
| submissions | id、owner_id、title、year、body、author、consent_version、consented_at、status、created_at、updated_at | owner取会话；新建固定pending |
| review_logs | id、submission_id、reviewer_id、action、note、created_at | 事务内追加；公开接口不暴露内部备注 |

删除策略必须先确定：原计划要求删除正文并保留匿名审核摘要。不要把完整原文永久复制进日志。备份中残留的数据也应有到期清理规则。撤回是停止展示，删除是删除内容，二者不能混为同一个操作。

审核竞争的实现要点：
- 使用事务。
- 条件更新：WHERE id = ? AND status = 'pending'，更新0行时返回409。
- 审核状态变更与审核流水在同一事务提交。
- 撤回后刷新公开结果和相关缓存。原型无服务器缓存；未来增加缓存时也必须失效。
- 对withdraw/delete检查owner_id，不能只检查“已登录”。
- 学生邮箱允许列表和是否接受校友账号需项目负责人确认，不能仅以任意字符串后缀作为身份验证。

## 4 数据组怎么完成

1. 根据内容组登记表编写导入脚本（Python或TypeScript均可）。
2. 导入前检查重复ID、空出处、悬空person/source引用、非法年份、未授权公开等。
3. 先在测试数据库导入；输出成功/失败明细，保留失败原因而非静默跳过。
4. 用事务保证一批数据不会只导入一半。保留原始文件、批次号、导入时间和负责人。
5. 每次内容改动用小测试集检查页面关联：事件→人物→关系→出处。
6. 中文搜索先在真实中文标题、姓名和短关键词上测试。少量数据可先按标题/姓名/摘要做参数化子串匹配；不能只启用默认全文检索就认定中文搜索达标。
7. 数据规模增大时再做中文分词、别名索引和服务端分页，并修改当前一次性catalog接口。

重要：前端Zod只能检查结构，不能证明内容真实、授权有效或关系正确；这些由内容流程和后端发布策略保障。

## 5 AI问答如何后续加入

当前版本没有AI页面、调用和密钥配置。
1. 只读数据通过验收后，再收集一组常见问答和没有答案的问题。
2. 知识库仅使用允许这样处理的资料，切块保留source_id与原文位置。
3. 后端完成检索与生成，浏览器只调用自建 /qa；大模型密钥不进入VITE_*或前端代码。
4. 展示回答及可点击来源，并检查来源是否真的支持回答。缺乏依据时明确提示无法回答。
5. 测试错误前提、同名人物、年代混淆、无资料问题、引用不存在、提示注入等情况。
6. 设置每用户频率、请求超时、单次token限制和月度费用上限。
7. 服务端错误时回退到检索或FAQ，不能编造答案填补空白。
8. 本地部署Embedding模型前先测内存和延迟，不能假定2核4G可以同时稳定承载所有模型服务。

AI上线前再确认供应商、预算、查询数据处理条款和用户告知。投稿授权不应自动解释为允许发送到外部大模型。

## 6 部署与安全

### 前端预览

pnpm build生成dist；pnpm preview只用于本地验收。HashRouter使页面链接形如 /#/people，静态服务器无需为这些前端路由做history回退。

### 正式部署建议

域名 → HTTPS反向代理 → 静态dist
                         → /api → Node服务 → PostgreSQL

可用Docker Compose组织Nginx、Node和PostgreSQL，但不建议首版同时引入所有可选服务。正式运行Node版本、基础镜像补丁和依赖需在部署时复核。

Nginx示例（域名、证书、实际服务地址按部署环境配置）：

~~~nginx
server {
    listen 80;
    server_name your-domain.example;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://backend:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
    }

    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;
}
~~~

这只是HTTP路由示例，**不是完整生产配置**。上线前配置HTTPS、HTTP跳转、请求体大小、限流和日志策略。proxy_pass不带尾斜杠，保留/api前缀，后端需以/api挂载路由。

后端必须落实：
- Cookie使用HttpOnly、Secure和适合部署方式的SameSite；不要把登录凭据放在可公开访问的构建文件中。
- 对写请求验证Origin并设计CSRF保护。若使用CSRF token，在HttpRepository中补取token及请求头后再启用真实写入。
- CORS只允许确切前端来源，带credentials时不能使用通配符。
- 所有角色/对象权限在服务器检查；禁止仅靠隐藏菜单保护审核接口。
- 数据库查询参数化；限流；错误日志不记录正文或邮箱验证码。
- 现在内容由React文本节点渲染，无原始HTML插入。未来接富文本时先做服务端和前端净化，不可直接dangerouslySetInnerHTML。
- 只向客户端输出可公开的来源信息，隐藏不等于未发送。
- 目录与投稿中链接限定为http/https；上线前检查下载与附件访问策略。
- 建立每日备份和恢复演练；备份不放在公开静态目录。

当前没有注册域名、购买服务器、部署公网或配置学校身份系统。学校授权、主办信息、服务域名和长期维护负责人需项目组自行落实。

## 7 一期验收顺序

1. 真实内容：至少10个事件，关联人物和出处能完整跳转，无演示条目混入。
2. 浏览：桌面和手机阅读无横向溢出，筛选为空有提示，搜索关键中文词能找到预期结果。
3. 身份：未登录不能投稿；普通用户直接调用审核API返回403。
4. 隔离：用户A不能读用户B的mine列表，不能撤回或删除B的记录。
5. 审核：pending不可公开；只有审核员可通过；退回有原因；旧页面重复审核返回409。
6. 撤回：通过后可展示，撤回后公开接口和搜索均不再返回。
7. 失败：断网、超时、存储故障不报告成功，用户正文不被清空。
8. 内容安全：测试HTML标签显示为普通文本而不执行；身份、邮箱和内部备注不进入公开JSON。
9. 性能：在明确手机/网络条件下检查首页加载；再逐步扩展至40—60事件、30—50人物。
10. 交接：跑通本地构建、数据导入、数据库恢复和新成员部署流程。

自动测试命令：pnpm test。原型测试覆盖本地状态流转、数据关联、错误处理和HTTP响应校验；它不能代替未来后端权限测试。

## 8 建议下一轮交付

- 内容组：10条已复核且可展示的事件和相应史料登记表。
- 后端组：catalog只读接口、登录验证原型、数据库迁移。
- 前端组：接真实catalog、补登录状态、使用真实资料做可读性测试。
- 数据组：导入脚本、引用完整性校验、中文搜索样例。
- 负责人：统一一期范围和人数，确定每周投入、资料授权负责人、审核责任人与验收日期。

需要补充的条件集中在进入真实数据/公网部署阶段：学校邮箱规则、首批资料及授权范围、审核员名单、域名/服务器、是否允许接外部AI。当前前端原型不依赖这些条件。
